# Deterministic personal exercise-loss forecast v1

Additive contract, 2026-10-27; independent of PR #10. The existing daily-summary and fallback APIs remain unchanged. No new provider, wearable export, storage table or dependency.

`POST /v1/forecasts` is authenticated by the existing local single-user session. Request: local `date`, IANA `timezone`, `history_days` (1–90; default 7), optional `exercise` and up to 32 historical `samples`. Any samples or actual weighing input requires `calibration_processing_consent:true` (strict boolean), separately from photo/Meta consent; clients must obtain it before uploading. Raw weighing data stays in request memory only and is not stored or sent to Meta. It reads one complete owned beverage snapshot and recomputes without persistence/cache. Never accept user-supplied intake totals. `exercise` has event UUID, aware `starts_at`, duration in minutes, duration provenance (`manual`; HTTP wearable export is gated), conditions (activity, low/moderate/high intensity, temperature C, relative humidity %), explicit comparability confirmation, optional categorical feedback and an optional `actual` sample. Samples contain event UUID, aware `observed_at`, identical conditions, the existing weighing-protocol inputs in kg/mL/min, and optional independently established absolute error bounds. No health identifiers, raw HealthKit samples, HR/HRV or arbitrary prompt fields are accepted. This endpoint does not call Meta or send data anywhere.

Core: `ai.hydration.personal_forecast.forecast_personal` receives confirmed logs, requested date/timezone, explicit aware clock and optional typed exercise/history. It reuses existing engine accounting/mass-balance code. Unknown composition remains null. Historical beverage totals describe only dates with logged intake, never estimated needs. Missing days are counted, never imputed as measured zero. Results preserve log revisions, date/timezone, UTC generation time, method version, assumptions and reasons.

Exercise result: `estimated` with lower/upper estimated **sweat-loss mL**, or `insufficient_data` with null bounds. Bounds propagate supplied absolute measurement errors and take the envelope of comparable observed sweat-rate intervals times target duration. These are conditional arithmetic bounds on the supplied measurements and constant-rate assumption, NOT a calibrated prediction/confidence interval or guaranteed future bound. No user-facing fluid target is created. Missing protocol, error bounds, environment, intensity, explicit comparability or usable observations yields insufficient_data. A completed actual measurement replaces that event's planned projection, never adds to it. Duplicate sample/event IDs are rejected.

Temperature/humidity/intensity/activity must match exactly; no arbitrary weather coefficients or matching tolerances. Caller additionally confirms comparability of wind, solar load, equipment, acclimatization, health and other relevant conditions. Exact weather fields alone do not prove comparability. The pure calculation core can accept a wearable-derived duration with provenance without networking; the HTTP adapter rejects `wearable_aggregate` pending separate privacy-policy review. Wearable integration/HealthKit export is not implemented. Feedback supplies uncertainty/context without numerical adjustments. No creatine/caffeine adjustment, retention multiplier, physiological daily baseline or medical diagnosis.

The daily requirement remains `insufficient_data` with null bounds, even when exercise loss can be estimated. No subtraction of intake from exercise losses is labeled a deficit/remaining requirement. Meta remains an optional, separately approved explanation consumer; this endpoint never changes PR #10's exact synthetic input or permit hashes. Only reviewed public method descriptions may be shared externally without new disclosure review.

Wire safeguards: extra-field rejection, finite bounded input sizes/numbers, strict booleans and explicit offsets; no raw-value errors. Domain upper limits are software request limits, not biological safety limits. Generated results carry `Cache-Control: no-store` from the existing request guard. Forecasts are not persisted; clients must discard and recompute after log/measurement edits. No current iPhone forecast UI is claimed.
