# Local trained Meta camera — v1

Owner assignment (2026-11-03): connect the selected trained adapter to Hydra and test on the physical iPhone, preserving exact label volume and Confirm/Edit. The existing request opts out of another design/approval discussion. This document records implementation choices, not new user approvals.

Use the existing FastAPI camera endpoint with additive `local_meta` mode and model `muse-glimmer-30b-beverage-lora-v1`. The iPhone sends its metadata-stripped prepared JPEG, after backend-photo consent, to its owner's Mac. Two sequential local MLX workers use the selected immutable base/checkpoint and fixed inference settings. The existing hosted Spark path and financial history are unchanged; local mode rejects enabled hosted billing, hydration and Wonder. No cloud fallback, API keys, downloads, retries, or concurrent local requests. The 30B model does not fit on the phone.

Approaches considered: ship weights on phone (incompatible with available memory); reuse hosted Spark (does not run the trained adapter); selected Mac inference behind the existing API (uses measured runtime and existing client flow). No new service dependency is required. Local Apple Vision text recognition supplies independent printed metric evidence. It does not train or replace the Meta identity model.

Pin adapter SHA256 `71a361e862c5e1399b25098601fd7d974253a5f5d285e9ad194f90e38028d48f`, verified base revision, executable, adapter config and encoder settings. Each request acquires a process lock spanning OCR, vision and language workers. Children inherit the lock descriptor so a backend crash cannot release their lease while they still run. Child environments exclude credentials. Bound execution by timeout and existing sampled MLX/RSS guards; an orphan keeps admission blocked until it exits or an operator stops it. Native validation routing uses a fresh single label-free `validation` row, solely an internal worker interface: live camera images do not enter benchmark manifests or scores.

Capacity is not remaining liquid or consumption. Use the existing conservative metric-label parser on local OCR, preserving literal label evidence. A model capacity without readable label evidence stays unknown. Conflicting OCR/model capacities stay unknown. Do not infer servings or multiply packages. Recognition remains unverified until the user confirms. Keep brand/product, confidence and correction provenance visible. Confirm/Edit retains full-container assumption labeling, unit editing, hydration-engine accounting, personal memory and separate default-off training consent. No automatic training or photo upload.

Successful local analysis produces a random receipt in the beverage database, separate from the financial ledger. It binds image hash, model/checkpoint, original result and time; confirmation validates this receipt and any submitted correction reference. Only literal corroborated unit spans are retained from OCR; unrelated background sentences are discarded. Retain at most 100 unconfirmed receipts, plus receipts referenced by saved logs. Durable idempotency replay uses the saved record independently of auxiliary receipts. Deleting a drink removes its receipt when no other saved drink references it; account data deletion removes every local receipt. Export includes local receipts. Raw JPEG, OCR files, intermediate features and per-run artifacts live in a private temporary directory and are removed on success/error; only separately opted-in training photos persist. OS termination can leave temporary files; a private runtime directory is cleared at backend restart while holding the local request lock.

Verification: nonbillable parser/runtime/API tests, real selected-checkpoint analysis of an owned image, iOS unit/UI tests and a physical build/install when the phone is available. Do not describe a simulator result as physical testing, or local calls as hosted requests.
