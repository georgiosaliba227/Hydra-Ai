# Comprehensive Wonder analysis contract

Implemented behind a disabled-by-default flag. This is additive to `WONDER_WORKOUT_API.md` and `HYDRATION_ANALYSIS_API.md`; the existing workout and trend routes retain their behavior. No real provider call or physical-device verification is established by the fake-transport tests described here.

`POST /v1/wonder/analysis/preview` accepts exactly `WorkoutForecastInput`, including its calibration-processing consent and bounded manual-history rules. The server rebuilds the nonbillable local analysis and allowlists its aggregate facts. The payload contains no raw samples, HealthKit records, identifiers, timestamps, timezone, beverage categories or caller-supplied provenance text. It includes the numerical engine's unchanged scalar facts, intake and documented nutrient totals with completeness flags, activity and environmental context, calibration counts, descriptive logged-day ranges, narrowly scoped completed-workout arithmetic and known missing-input codes. Optional numeric typical-workout medians reuse the older planned-workout preview; environmental and duration comparisons use its display thresholds and never change the forecast. Optional trend context reuses the existing trend calculation, sanitized to latest/preceding week totals and logged-day counts, deterministic percentage change and time-of-day volume buckets. Logging coverage remains unverified. The complete facts version is `wonder-analysis-facts-v2`; changed included aggregates change the consent hash.

The response version is `wonder-analysis-preview-v2`. It includes `facts`, `payload_sha256`, `model`, `status`, `explainable`, `reason`, `input_bound_tokens`, `max_output_tokens`, `worst_case_micro_usd`, `per_request_cap_micro_usd`, `live_available`, `dispatch_supported`, `verified_for_billing`, `cost_estimate_policy`, `account_id` and `saved`. A cost bound exceeding the existing per-request cap makes the preview unavailable. The estimate uses existing reference prices, is explicitly not a verified live quote and does not authorize spending. Pure offline previews and mocks remain available for missing-data explanation; the HTTP dispatch path requires a personal observation, a logged beverage/day or an actual estimated measurement. Empty records and synthetic previews cannot dispatch.

`POST /v1/wonder/analysis` accepts the personal request plus the exact preview SHA-256 and strict boolean `consent_to_send: true`. It recomputes current included facts, rejects stale consent, and replays a validated result for the same payload without a new request. New dispatch additionally requires `HYDRA_WONDER_ANALYSIS_ENABLED=true` (default `false`), the existing live configuration, selected account, independently reviewed key/model/quote/input consent, and all existing spending safeguards. Invalid values for the new flag fail startup closed. The flag does not enable old live configuration or billable requests by itself. Leaving it false prevents new comprehensive dispatch even when an older Wonder feature is configured. Saved replay remains possible without enabling new spending.

The result envelope is `{replayed, saved, result}`. `result.version` is `wonder-analysis-v2`; it carries facts, payload hash, UTC generation time, eight sections, provenance, provider observations and fixed limitations. Each section contains `id`, `title`, `template`, `text`, `evidence_status` and ranked `insights` objects (`id`, `title`, `template`, `text`). The IDs are `summary`, `workout_loss`, `activity`, `environment`, `beverages`, `trends`, `uncertainty` and `measurement`.

Muse Wonder ranks one to three distinct, evidence-applicable insight IDs in every section. Choices change which supported information is emphasized: estimates versus limited comparable history, missing or documented composition, historical duration and environmental differences, descriptive weekly logged-volume changes, logged timing patterns and measurement gaps. The dynamic schema offers only IDs computed applicable from the facts. Hydra maps IDs to vetted factual scaffolds, authors the factual clauses and supplies every number. Exact per-section membership and uniqueness reject arbitrary prose, cross-section IDs, unsupported comparisons, duplicate IDs and omitted sections. Numeric, Unicode numeric, medical, diagnostic, prescriptive and causal prose cannot pass the ID allowlist. Required scope, weather, logging and uncertainty caveats are appended independently of the model selections. A supplied provider reply must have the reviewed model and complete strict envelope; there is no repair, model fallback or retry. Provenance states `selection_origin: muse_wonder_selected_scaffolds` and `text_origin: hydra_vetted_scaffolds_and_facts`. This is not free-form model-authored scientific interpretation.

The numerical engine and stored numerical facts keep their precision. Displayed mL values are rounded to whole mL, with range endpoints rounded outward; nutrient and environmental displays use at most one decimal. Display rounding is deterministic and labeled. Unknown nutrient totals remain null, including partial nutrient coverage; known subtotals never masquerade as complete totals. Intake, retention, planned loss and hydration status remain distinct. Signed completed-workout arithmetic is not clamped to zero and omits urine and other losses.

Dispatch reuses `WonderHydrationGateway._run`, `register_workout_case`, the current quote/account configuration and shared Wonder lock. Rich analysis and older personal workout/trend requests hold that lock from their fact snapshot through saved-result publication. Confirmed owner deletion acquires the same lock before any backend mutation and returns `wonder_busy` (409) while a request or publication is active; it can be retried after completion. This prevents saved aggregates from appearing after a successful deletion. Identity is checked before reservation; invoice finality, unresolved attempts, frozen accounts, cutoffs, notices and duplicate-case rules are unchanged. Synthetic and empty facts are also rejected by the gateway method. The transport accepts only exact reconstruction of the server payload. There is no new ledger schema, financial policy, account rotation, administrative operation or credential path. Cross-ledger human checks remain required where existing policy requires them.

Successful validated results use the existing owner-private result directory, named `analysis-<payload_sha256>.json`. Records are size-bounded, written to a private temporary file, flushed and atomically published without replacing an existing file. Loads reject symlinks, malformed/oversized records, wrong payloads, changed facts, templates, rendered text and provenance. Saved consistency does not independently attest provider authenticity or invoice settlement. `/v1/export` adds `wonder_analysis_explanations`; confirmed `/v1/data` deletion adds `deleted_analysis_explanations`, and never deletes financial history. Confirmed deletion also clears regular `.pending-` result files left by interrupted publication, while skipping symlinks and unrelated files.

Errors use the shared authenticated, no-store error envelope: `analysis_preview_stale` (409), `analysis_insufficient_data` (422), `wonder_unavailable` (503), `wonder_busy` (409), `wonder_blocked` (409), and `wonder_attempt_unresolved` (502, with an attempt ID). The last outcome must not trigger an automatic retry. Bodies are limited to 128 KiB, matching the existing bounded history routes.

Tests cover disposable-ledger dispatch/settlement, duplicate replay, stale included logs, a blocked second attempt after unresolved dispatch, identity mismatch before reservation, concurrent sharing with the old workout lock, rejected provider prose, tampered saved results, export/deletion, empty/synthetic/over-cap rejection, invalid flags and strict consent, including deterministic provider/publication interleavings for deletion and the older personal Wonder routes. Display tests cover fractional amounts, rounded-zero percentage changes and exact boundaries shared with the older workout comparisons. Offline grammar evaluation separately exercises 400 ranked selections (every permitted per-section ranking against fixed choices elsewhere), 3200 rendered sections and 384 rejected adversarial selections. The full cross-section Cartesian product is not enumerated. Those results assess software grounding invariants; they do not measure numerical predictive accuracy, real Muse Wonder response quality or clinical validity.

Remaining live evidence includes account-specific current ledger/identity/quote and billing-finality review, previewed aggregate disclosure consent, the new feature flag's explicit enablement, and a separately authorized actual provider attempt. Current implementation and mock tests do not satisfy those gates or establish App Store/HealthKit disclosure compliance. Real-device verification remains separate.
