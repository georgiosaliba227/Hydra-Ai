## Cost investigation

The original $1.312896 was an admission reservation, not a measured beverage-image charge. It priced all 1,048,576 context tokens as uncached input and added 512 output tokens. That included 512 unnecessary input positions: Meta requires input plus requested output to fit in the same context window. The corrected conservative single-shot token bound is:

| Component | Verified limit/rate | Maximum USD |
|---|---|---:|
| Input | (1,048,576 − 512) × $1.25 / 1,000,000 | 1.310080 |
| Reasoning and visible output combined | 512 × $4.25 / 1,000,000 | 0.002176 |
| Token total | Integer microdollar ceiling | **1.312256** |
| Other charges | Independently verified account-specific bound required | Unknown until verified |

Sources rechecked: [model context and Standard ID](https://dev.meta.ai/docs/models), [shared context/output-token constraint](https://dev.meta.ai/docs/protocols/responses), [Standard pricing](https://dev.meta.ai/docs/pricing-rate-limits), [reasoning accounting](https://dev.meta.ai/docs/reasoning). The bound assumes exactly the enforced single model pass with no tools/history; hosted tool iterations would invalidate it and are forbidden. Cached-input discounts are not assumed. The $0.25 limit and all account thresholds are unchanged. **The corrected bound still fails admission.** Unknown additional charges independently fail closed.

The $0.25 limit with 512 output tokens and no other charges would require a proven whole-request input bound of at most **198,259 tokens**: rounding up gives exactly $0.250000; 198,260 gives $0.250001. This is a break-even calculation, NOT evidence that an image meets it.

### Image and prompt limits

The current iPhone redraws orientation-correct pixels with a maximum 1600-pixel long edge, then tries JPEG quality 0.8/0.6/0.4/0.2 within 1 MiB. The backend independently validates one JPEG <=1 MiB and dimensions <=2048 on each axis, then strips APP/EXIF/XMP/IPTC/comments. The exact normalized image hash is bound to the first-test permit. No URLs, Files calls, history, tools, SAM or user-supplied free-text prompt enter the live request.

[Image understanding](https://dev.meta.ai/docs/image-understanding) documents image inputs and approximate resolution-based token examples, not an enforced formula bounding all deployments. [Token counting](https://dev.meta.ai/docs/token-counting) says multimodal tokenization varies with model version, preprocessing and template. Compressing JPEG bytes does not establish token count. A smaller thumbnail could reduce expected cost but harm readable brand/volume labels; it cannot prove the missing billing bound. The working capture/photo flow is therefore unchanged.

The prompt is fixed at 383 UTF-8 bytes, with no arbitrary client text. The compact strict JSON schema is 894 serialized bytes (previously 1100): generated display titles were removed; nullable fields, bounds, required keys, references and extra-field rejection remain. Bytes/characters are not converted to tokens using an assumed ratio. No unsupported `max_input_tokens` or `detail: low` control is relied on.

Reasoning now explicitly uses the documented `reasoning.effort: minimal`. `none` is unsupported. The fixed 512 output-token limit includes both reasoning and visible output; there is no extra hidden 512-token allocation. Keeping 512 accommodates structured uncertainty; reducing it further cannot solve the input bound and risks truncation. No reasoning summary or encrypted replay is requested. Model accuracy/completeness with these settings remains unverified until an authorized real evaluation.

### Why preflight does not remove the blocker

The image guide presents `/v1/responses/input_tokens` as a useful estimator, but the dedicated token-counting guide explicitly distinguishes context occupancy from billing and advises using counts for context fit. It also discusses accounting adjustments and iteration-dependent usage. No reviewed provider guarantee currently establishes a deterministic billing ceiling from that count for this exact model/request/deployment, and the endpoint's own account-specific charge/retention status is unverified. No preflight was called, and no automated preflight spending/disclosure path was added.

To remove the blocker, obtain provider documentation or written account-specific confirmation of an enforceable whole-request billable-input ceiling (including media, prompt/template, reasoning and charge categories) below the calculated threshold; or an independently reviewed counting/billing method with its own charge and privacy bounds. Implement it in BOTH gateway reservation and the actual sender, bind its evidence to exact request/model/version/expiry, and re-run fault tests. A guessed pixel multiplier, observed sample cost, client-supplied token count or lower arbitrary reservation is insufficient. Do not raise the authorization limit as a workaround.
